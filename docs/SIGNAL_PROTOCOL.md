# Signal Protocol

The contract between any signal producer (analytics SDK, manual UI,
external bot) and the trade adapter. **One schema, one endpoint, one
universe of intents.**

---

## `UniversalSignal`

Wire format is JSON. Adapter-side dataclass is `slots=True, frozen=True`.

```python
@dataclass(slots=True, frozen=True)
class UniversalSignal:
    signal_id: str            # UUID v4, generated by producer
    source: str               # producer identifier (e.g. "adaptive_sdk")
    symbol: str               # exchange symbol (e.g. "BTCUSDT")
    venue: Venue              # "binance_um" | "bybit_linear"
    direction: Direction      # "LONG" | "SHORT"
    intent: Intent            # "OPEN" | "ADD" | "REDUCE" | "CLOSE" | "REVERSE"
    sizing: SizingSpec        # exactly one of FixedQty / NotionalUsd / PctEquity / RiskBased
    sl: Optional[StopSpec]    # stop-loss spec; None = no stop
    tp: Optional[StopSpec]    # take-profit spec; None = no TP
    ttl_seconds: float        # signal expires if not actioned within TTL
    correlation_id: Optional[str] = None
                              # producer-side trace id, threaded through
                              # every derived order / fill / outcome.
                              # Defaults to signal_id if omitted.
    metadata: dict[str, str] = field(default_factory=dict)
                              # opaque, free-form (audit only)
```

`correlation_id` lets a producer (e.g. `adaptive_sdk`) recognize the
outcome of one of its own signals after the trade has closed; without
it, the MAB feedback loop in the analytics SDK cannot learn. If the
producer does not set it, the adapter substitutes `signal_id`.

## Enums

### `Venue`

```
"binance_um"     - Binance USD-M Futures
"bybit_linear"   - Bybit USDT-Perpetual
```

### `Direction`

```
"LONG"   - long position (buy to open)
"SHORT"  - short position (sell to open)
```

### `Intent`

```
"OPEN"     - open a new position; if existing same-direction, treated as ADD
"ADD"      - explicitly scale in to an existing same-direction position
"REDUCE"   - close part of an existing position
"CLOSE"    - close all of an existing position
"REVERSE"  - close existing and open opposite-direction at same size
```

**Intent resolution** happens in `signal_router`:
- `OPEN` against `IDLE` → `OPEN`
- `OPEN` same direction as `OPEN` position → `ADD`
- `OPEN` opposite direction from `OPEN` position → `REVERSE`
- `ADD` against `IDLE` → rejected
- `REDUCE` against `IDLE` → rejected
- `CLOSE` against `IDLE` → rejected (idempotent no-op acceptable, but
  for clarity it's a 422)
- `REVERSE` against `IDLE` → treated as `OPEN`

## Sizing

Exactly one of these four variants must be set on each signal.

### `FixedQty`

Literal quantity in base asset.

```json
{ "kind": "fixed_qty", "qty": 0.5 }
```

Rounded to symbol's step size before submission.

### `NotionalUsd`

Literal USD-equivalent notional. Adapter divides by the cached BBO mid
(or the venue's mark price if the BBO has not arrived yet) at signal-
receipt time and rounds the resulting `qty` to the venue's `stepSize`.
This is the natural mode for UI-driven flows where the operator types
a dollar amount directly.

```json
{ "kind": "notional_usd", "notional_usd": 500.0 }
```

Computation:
```
entry_price = best_ask (long) | best_bid (short)
qty         = round_step( notional_usd / entry_price, stepSize )
```

### `PctEquity`

Percentage of total equity (account-wide for the venue).

```json
{ "kind": "pct_equity", "pct": 2.0 }
```

`2.0` = 2% of equity. Equity is fetched at signal-receipt time.

### `RiskBased`

Sized so that hitting the stop-loss costs exactly `risk_usd`. Requires
`sl` to be set on the signal (otherwise rejected).

```json
{ "kind": "risk_based", "risk_usd": 50.0 }
```

Computation:
```
sl_distance_pct = |sl_price - entry_price| / entry_price
notional = risk_usd / sl_distance_pct
qty = notional / entry_price   (then rounded)
```

Where `entry_price` is the current best bid (for short) or best ask (for
long) at signal-receipt time.

## Stops (`StopSpec`)

Used for both `sl` and `tp`. Multiple specification modes:

### `AbsolutePrice`

```json
{ "kind": "absolute", "price": 64500.0, "mode": "native" }
```

### `BpsFromEntry`

```json
{ "kind": "bps", "bps": 50, "mode": "native" }
```

50 bps = 0.5%. Sign inferred from `direction` (long: SL below, TP above).

### `PctFromEntry`

Ergonomic alias of `BpsFromEntry` for UI-driven flows where the
operator types a percentage directly. Internally converted to
`BpsFromEntry` at parse time (`pct × 100 = bps`).

```json
{ "kind": "pct", "pct": 0.5, "mode": "native" }
```

`0.5` = 0.5% from entry.

### `AtrMultiple`

```json
{ "kind": "atr_multiple", "multiple": 1.5, "atr_period_seconds": 60, "mode": "native" }
```

ATR computed from a per-symbol rolling window of recent trades by the
adapter. Useful for adaptive stops.

### `Mode`: `"native"` | `"local"`

- `native` (default) — placed as a real stop order on the exchange.
  Safer; survives adapter crashes.
- `local` — adapter watches price internally and emits a market close on
  trigger. Useful for trailing stops or stops that move frequently.

---

## TTL

`ttl_seconds` is the maximum age the signal is willing to be processed.
Common values:

- Funding-event capture: `1.5` (must act within 1.5s or skip)
- Mean-reversion scalp: `5.0` (acceptable to act within 5s)
- Slow swing entry: `60.0`

If the signal arrives at the adapter and `now - received_at > ttl_seconds`
during routing (e.g. due to retry queueing), it is rejected with
`rejection_reason: "TTL_EXPIRED"`.

## Example payloads

### Open a long with risk-based sizing and BPS stops

```json
{
  "signal_id": "5f1d2c3a-...",
  "source": "adaptive_sdk",
  "symbol": "BTCUSDT",
  "venue": "binance_um",
  "direction": "LONG",
  "intent": "OPEN",
  "sizing": {
    "kind": "risk_based",
    "risk_usd": 25.0
  },
  "sl": { "kind": "bps", "bps": 30, "mode": "native" },
  "tp": { "kind": "bps", "bps": 60, "mode": "native" },
  "ttl_seconds": 3.0,
  "metadata": {
    "arm_id": "1",
    "confidence": "0.78",
    "exhaustion_type": "SELL_EXHAUSTION"
  }
}
```

### External UI: $-notional + %-stops

Operator chose `BTCUSDT` on Binance UM, set `$500` trade size,
`SL = 0.5%`, `TP = 1.0%`, then the strategy fired BUY:

```json
{
  "signal_id": "...",
  "source": "external_ui",
  "symbol": "BTCUSDT",
  "venue": "binance_um",
  "direction": "LONG",
  "intent": "OPEN",
  "sizing": { "kind": "notional_usd", "notional_usd": 500.0 },
  "sl": { "kind": "pct", "pct": 0.5, "mode": "native" },
  "tp": { "kind": "pct", "pct": 1.0, "mode": "native" },
  "ttl_seconds": 3.0,
  "metadata": { "ui_session": "op-1-2026-05" }
}
```

The adapter converts `notional_usd → qty` from the cached BBO and
the `pct` stops to absolute prices at submission time, then ships
entry + SL + TP in one `place_order` (on Binance UM as `STOP_MARKET
closePosition=true` parallel to the entry, per A8).

### Manual close from UI

```json
{
  "signal_id": "...",
  "source": "manual_ui",
  "symbol": "BTCUSDT",
  "venue": "binance_um",
  "direction": "LONG",
  "intent": "CLOSE",
  "sizing": { "kind": "pct_equity", "pct": 100.0 },
  "sl": null,
  "tp": null,
  "ttl_seconds": 30.0,
  "metadata": { "user": "operator-1" }
}
```

(Sizing for CLOSE is informational only — `100%` means close everything.)

### Reverse on stronger contra-signal

```json
{
  "signal_id": "...",
  "source": "external_bot",
  "symbol": "ETHUSDT",
  "venue": "bybit_linear",
  "direction": "SHORT",
  "intent": "REVERSE",
  "sizing": { "kind": "fixed_qty", "qty": 0.5 },
  "sl": { "kind": "absolute", "price": 3500.0, "mode": "native" },
  "tp": null,
  "ttl_seconds": 5.0,
  "metadata": { "reason": "regime_flip" }
}
```

## Adapter responses

### Accepted

```json
{
  "accepted": true,
  "signal_id": "...",
  "intent_resolved_to": "OPEN",
  "expected_qty": 0.5,
  "expected_notional_usd": 32500.0,
  "submitted_at": 1700000000.123
}
```

The signal has been validated, sized, accepted by the position manager,
and an order is being placed asynchronously. Observe outcome via
`WS /v1/events`.

### Rejected

```json
{
  "accepted": false,
  "signal_id": "...",
  "rejection_reason": "EMERGENCY_NOTIONAL_LIMIT",
  "details": "Notional 75000 USD exceeds max_single_order_notional_usd=50000."
}
```

Rejection reasons:

| Code | Meaning |
|---|---|
| `SCHEMA_INVALID` | JSON didn't parse / missing fields |
| `UNKNOWN_VENUE` | Venue not enabled in this adapter |
| `UNKNOWN_SYMBOL` | Symbol not registered with exchange |
| `INTENT_INCOMPATIBLE_WITH_STATE` | e.g. CLOSE on IDLE position |
| `SIZING_REQUIRES_SL` | `risk_based` without `sl` |
| `TTL_EXPIRED` | Signal too old by routing time |
| `EMERGENCY_NOTIONAL_LIMIT` | Hit max single order notional |
| `EMERGENCY_LEVERAGE_LIMIT` | Symbol leverage exceeds max |
| `INSUFFICIENT_BALANCE` | Sized amount exceeds available margin |
| `EXCHANGE_DOWN` | Connectivity check failed |

## Idempotency

Producers SHOULD generate stable `signal_id`s and retry on network errors
with the same `signal_id`. The adapter:

1. On second request with same `signal_id`, returns the cached previous
   response (same `accepted` flag, same `intent_resolved_to`, same
   `expected_qty`).
2. Cache TTL = `signal_idempotency_ttl_seconds` from config
   (default 3600).
3. After cache expiry, the same `signal_id` is treated as a new signal.

Implementation (decision A5 + requirement D.6): a bounded in-memory
`dict[signal_id, CachedResponse]` answers in microseconds on the
synchronous accept path; a SQLite mirror persists the cache so it
survives an adapter restart. Reload on startup is one bulk SELECT,
not per-signal lookups.

This protects against duplicate routing under producer-side retries and
network blips. It does NOT protect against a producer intentionally
sending two distinct signals with the same ID — that's a producer bug.

## Event protocol (embedded mode and `WS /v1/events`)

In embedded mode, every channel below is exposed as an `async`
iterator on `uta.TradeAdapter` (`subscribe_orders`,
`subscribe_positions`, `subscribe_book`, `subscribe_trades`,
`subscribe_bbo`, `subscribe_outcomes`, `subscribe_alerts`).

In gateway mode the same payloads are framed as JSON messages on
`WS /v1/events`. Market-data channels (`book_update`, `trade_print`,
`bbo_update`) are opt-in per connection — the consumer sends a
`subscribe` message specifying `{venue, symbol, channels}`.

Event types:

### `signal_accepted`
```json
{ "type": "signal_accepted", "ts": ..., "data": { "signal_id": ..., "intent_resolved": ..., "qty": ..., "notional_usd": ... } }
```

### `signal_rejected`
```json
{ "type": "signal_rejected", "ts": ..., "data": { "signal_id": ..., "rejection_reason": ..., "details": ... } }
```

### `order_update`
```json
{ "type": "order_update", "ts": ..., "data": { "client_order_id": ..., "exchange_order_id": ..., "status": "ACK"|"FILLED"|"PARTIALLY_FILLED"|"CANCELLED"|"REJECTED", ... } }
```

### `fill`
```json
{ "type": "fill", "ts": ..., "data": { "fill_id": ..., "client_order_id": ..., "qty": ..., "price": ..., "fee": ..., "fee_asset": ... } }
```

### `position_update`
```json
{
  "type": "position_update",
  "ts": ...,
  "data": {
    "venue":            "binance_um",
    "symbol":           "BTCUSDT",
    "side":             "LONG" | "SHORT" | "FLAT",
    "qty":              0.5,
    "entry_price":      64500.0,
    "state":            "OPEN",
    "unrealized_pnl_usd": 142.0,
    "margin_used_usd":    1612.5,
    "liquidation_price":  61240.0,
    "correlation_id":     "5f1d2c3a-..."
  }
}
```

`unrealized_pnl_usd`, `margin_used_usd`, and `liquidation_price` come
from the venue's user-data stream (Binance `ACCOUNT_UPDATE`,
Bybit `position` topic). The adapter does **not** invent them — if
the venue temporarily omits them (e.g. on a reconnect), the field is
`null` and a reconcile-driven update arrives shortly after.

### `alert`
```json
{ "type": "alert", "ts": ..., "data": { "severity": "info"|"warning"|"critical", "code": ..., "message": ... } }
```

### `reconcile_diff`
```json
{ "type": "reconcile_diff", "ts": ..., "data": { "venue": ..., "kind": "ORDER_MISSING_LOCAL"|"POSITION_QTY_MISMATCH"|..., "details": ... } }
```

### `book_update`

Top-N book snapshot or per-level deltas (subscription chooses).

```json
{
  "type": "book_update",
  "ts": ...,
  "data": {
    "venue": "binance_um",
    "symbol": "BTCUSDT",
    "kind": "snapshot" | "delta",
    "bids": [[price, qty], ...],
    "asks": [[price, qty], ...],
    "ts_event": 1700000000.012,    // exchange-side ts (ms-precision float)
    "ts_recv":  1700000000.018,    // adapter-side ts on WS arrival
    "seq":      4839128
  }
}
```

### `trade_print`

A single trade print on the public tape.

```json
{
  "type": "trade_print",
  "ts": ...,
  "data": {
    "venue": "binance_um",
    "symbol": "BTCUSDT",
    "price": 64512.3,
    "qty": 0.014,
    "is_buyer_maker": true,         // Binance convention; True => seller initiated
    "trade_id": "...",
    "ts_event": 1700000000.012,
    "ts_recv":  1700000000.018
  }
}
```

### `bbo_update`

Throttled best-bid/ask snapshot (default 10 ms cadence).

```json
{
  "type": "bbo_update",
  "ts": ...,
  "data": {
    "venue": "binance_um",
    "symbol": "BTCUSDT",
    "bid_price": 64511.9, "bid_qty": 1.42,
    "ask_price": 64512.1, "ask_qty": 0.83,
    "ts_event": 1700000000.020,
    "ts_recv":  1700000000.022
  }
}
```

### `outcome_report`

Emitted once when a position closes (state machine reaches `IDLE` after
`CLOSING`). Carries the realized economics plus extrema sampled during
the lifetime of the position so the analytics SDK's MAB can learn.

```json
{
  "type": "outcome_report",
  "ts": ...,
  "data": {
    "correlation_id":  "5f1d2c3a-...",   // mirrors UniversalSignal.correlation_id
    "signal_id":       "5f1d2c3a-...",   // origin signal
    "venue":           "binance_um",
    "symbol":          "BTCUSDT",
    "side":            "LONG",
    "qty":             0.5,
    "entry_price":     64500.0,
    "exit_price":      64880.0,
    "pnl_usd":         190.0,            // realized PnL after fees, in quote
    "fees_usd":        2.30,
    "slippage_bps":    1.2,              // |fill_price - intended_price| / intended
    "mfe_usd":         245.0,            // max favorable excursion in quote
    "mae_usd":         -35.0,            // max adverse excursion in quote
    "holding_time_ms": 18420,
    "close_reason":    "sl" | "tp" | "manual" | "signal" | "reconcile" | "liquidation",
    "opened_at":       1700000000.018,
    "closed_at":       1700000018.438
  }
}
```

MFE / MAE are computed by the adapter sampling mid-price from the
BBO stream on every tick during the position's lifetime. The adapter
automatically subscribes the relevant `(venue, symbol)` BBO channel
for the duration of any open position (decision A22), so MFE / MAE
reflect real ticks rather than the position's own fills. The sampler
runs in-process; no extra exchange call.

## Versioning the protocol

The protocol itself is versioned independently of the adapter codebase:

- v1.0 schema is what's documented here.
- Additive changes (new optional fields, new intents that gracefully
  degrade) → v1.1, v1.2, ... New optional fields default to `None`,
  never break existing producers.
- Breaking changes (rename, remove, semantic change) → v2.0.

A golden-snapshot test in `tests/protocol/test_schema_lock.py` will
fail any change to the v1.0 wire shape (field names, types,
ordering of tagged-union variants) so a casual edit can't
accidentally bump the protocol. Intentional bumps update both the
golden file and the table above.

The adapter advertises its supported protocol version in both modes:

- Embedded: `uta.PROTOCOL_VERSION` (a module-level string).
- Gateway: `GET /v1/health` returns `{ "protocol_version": "1.0", ... }`.

Producers SHOULD check this on startup and refuse to send if their
expected version is incompatible.
